= Version Pinning
:navtitle: Version Pinning
:description: How to pin the Valentus Theme UI bundle — dual-axis labels, exact versions, rolling lines, Renovate, and semver contract.

GitHub Releases distribute this theme as `ui-bundle.zip`.
There is no npm-style range syntax (`^1.0`, `~1.0`) in the URL itself—you choose how much automation you want around a zip URL.

== Version identity (dual-axis)

Valentus uses **two independent majores** so they do not get conflated:

[cols="1,2,2", options="header"]
|===
| Axis | What it means | Where it appears

| Valentus semver
| `MAJOR.MINOR.PATCH` — chrome/partial/CSS contract for theme *modders*
| `package.json`, git tag `vX.Y.Z`, download path `.../vX.Y.Z/ui-bundle.zip`

| Antora compatibility
| `+antora.N` — Antora *framework* major this release targets
| Public label, changelog, GitHub Release *title*, `supported-lines.json`
|===

*Full public label:* `VALENTUS_SEMVER+antora.N` — example *2.0.0+antora.3*.

*Bump Valentus MAJOR* when extending Valentus breaks (partials, CSS hooks, layout chrome). The visual redesign is Valentus *2.0.0* even though Antora is still 3.

*Change `+antora.N`* when the supported Antora framework major changes. Prefer keeping Valentus major independent: Antora 4 support might be `2.1.0+antora.4` if Valentus APIs stay compatible, or `3.0.0+antora.4` if Valentus also breaks for Antora 4.

*Historical 1.x:* every 1.x release targeted Antora 3 → documented as `1.x.y+antora.3`. Git tags were *not* renamed (`v1.1.2` still downloads that asset).

Machine-readable map: link:https://github.com/antora-supplemental/valentus-theme/blob/main/supported-lines.json[`supported-lines.json`].

== What `snapshot: true` is (and isn't)

`ui.bundle.snapshot: true` tells Antora to re-fetch the bundle URL on each build instead of caching the zip forever.

* *Is:* re-download this URL each build.
* *Isn't:* semver range resolution or "latest within v2.0.x."

With an exact pin, `snapshot: true` still matters if a release asset is ever replaced (rare).
With `releases/latest`, it is what makes every deploy pick up new releases.

== Consumer strategies

Think of this as a stability vs. freshness tradeoff—the same as any dependency, distributed as a zip URL.

=== 1. Float on latest (fastest, least control)

[source,yaml]
----
ui:
  bundle:
    url: https://github.com/antora-supplemental/valentus-theme/releases/latest/download/ui-bundle.zip
    snapshot: true
----

*Gets:* every release automatically on the next docs deploy.
*Risk:* a new Valentus minor or major (for example 2.1.0 or 3.0.0) can land without you noticing.
*Good for:* light consumers who watch releases closely.

=== 2. Pin exact version (most control)

[source,yaml]
----
ui:
  bundle:
    url: https://github.com/antora-supplemental/valentus-theme/releases/download/v2.0.0/ui-bundle.zip
    snapshot: true
----

Pin URLs use the *semver tag* (`v2.0.0`), not the `+antora.N` label.
*Gets:* nothing new until you change the URL.
*Risk:* lowest—you know exactly what CI builds.
*Good for:* sites with heavy supplemental overrides that assume specific partials, CSS, or JS.

=== 3. Pin a rolling line (recommended default)

Use the maintainer rolling tag for the Valentus major line you want:

[source,yaml]
----
ui:
  bundle:
    url: https://github.com/antora-supplemental/valentus-theme/releases/download/v2/ui-bundle.zip
    snapshot: true
----

*Gets:* latest **v2.x.x** (minors and patches within Valentus major 2) on each build.
*Risk:* low for most sites—semver contract keeps minors additive; Valentus majors get a new line tag (`v3`, …).
*Good for:* most production sites that want fixes without hand-editing the playbook every patch.

Stay on Valentus 1.x (pre-redesign) with `.../v1/ui-bundle.zip` until you schedule a migration.

This is the **recommended default** and what install docs show for current releases.

=== 4. Pin a sub-line, float patches (narrower range)

You want: stay on v2.0 assumptions, pick up v2.0.x bugfixes, do not auto-jump to v2.1.0.

GitHub does not offer `releases/latest-v2.0/`.
Implement the range yourself:

==== Option A — Renovate / Dependabot (recommended)

Treat the version in `antora-playbook.yml` like a dependency.
Configure Renovate with a regex manager on the bundle URL—see link:https://github.com/antora-supplemental/valentus-theme/blob/main/examples/renovate.json[`examples/renovate.json`] in this repository.

* `~2.0.0` — patches only within v2.0.x
* `^2.0.0` — patches and minors within v2.x

Renovate opens a PR when a matching release ships.
You review the changelog, run a local build, merge when ready.

==== Option B — Prebuild resolver script

Call the GitHub API for releases, filter tags matching `v2.0.*`, pick the highest patch, write the URL into the playbook or an env var.
Fully automatic patch pickup within the line; you own the script.

==== Option C — Rolling maintainer tags (first-class line pin)

This theme publishes **moving** Git tags and prerelease aliases (updated by the release workflow):

[cols="2,3", options="header"]
|===
| Pin URL | Resolves to

| `.../releases/download/v2.0/ui-bundle.zip`
| Latest **v2.0.x** patch

| `.../releases/download/v2/ui-bundle.zip`
| Latest **v2.x.x** (minor + patch within Valentus major 2)

| `.../releases/download/v1/ui-bundle.zip`
| Latest **v1.x.x** (legacy pre-redesign line)
|===

Rolling releases are marked *prerelease* so `releases/latest` still tracks normal semver tags.

WARNING: Moving tags trade reproducibility for convenience.
Prefer exact pins or Renovate PRs when CI must be bitwise stable.

== Semver contract (maintainer)

Git tags are pure Valentus semver (`v2.0.0`, …). Release titles use the dual-axis label (`2.0.0+antora.3`).

[cols="1,2,2", options="header"]
|===
| Release | Should mean | Consumer can

| Patch (`v2.0.1` / `2.0.1+antora.3`)
| Bugfix; no partial/CSS/`adt-*` hook breaks
| Auto-adopt if pinned to `~2.0.0` via Renovate

| Minor (`v2.1.0` / `2.1.0+antora.3`)
| Additive, backward compatible for modders (new `site.keys`, docs)
| Adopt when ready (`^2.0.0` or manual)

| Valentus major (`v3.0.0` / `3.0.0+antora.N`)
| Breaking partial/CSS/JS contract for theme extenders
| Never auto; explicit migration

| Antora suffix only (`2.x.y+antora.4`)
| Same Valentus contract; new Antora framework major supported
| Review Antora upgrade notes; Valentus major may stay put
|===

Sites with forked supplemental partials should still review *patches*—renamed `adt-*` classes or header structure changes can affect overlays.

== Practical workflow (example)

For a site with deep supplemental overlays:

. Pin rolling line `v2` in `antora-playbook.yml` (or exact `v2.0.0` if overrides are brittle). Stay on `v1` until you port overlays for the redesign.
. Add Renovate with `~2.0.0` or `~2.1.0` on the playbook URL (see `examples/renovate.json`).
. On each Renovate PR: read the theme changelog (including the `+antora.N` label), run `antora` locally, spot-check header, nav, tool-band, and dark mode.
. Bump Valentus minor/major only when you schedule it—treat like a small migration (port supplemental JS/CSS if needed).
