= GitHub Topics (Dependents)
:navtitle: GitHub Topics
:description: Tag sites that use Valentus with the valentus-theme GitHub topic so dependents stay rediscoverable.

Sites that pin the Valentus `ui-bundle.zip` (or vendor Valentus `supplemental-ui`) without a compose pack should add the GitHub *repository topic* `valentus-theme`.
That is separate from gallery classification topics (`antora-theme`, `antora-light-theme`, …).

== Why

GitHub Search (`topic:valentus-theme`) is the fastest way to find every docs playbook that depends on this theme when chasing regressions (for example font-size chrome, `head-meta` overlays, or rolling `v3` pins).

Without the product topic, dependents only show up via brittle code search for the release URL.

== What to set (consumers)

On the repository that owns the Antora playbook:

. Open *About* → *Topics* (or `Settings` → general topics).
. Add **`valentus-theme`** (exact repo/product name, kebab-case).
. Optionally add `antora-docs` / `antora-site` if you want broad Antora site discovery.

== Provider rule (facto-stack hubs)

Tag the **provider** your playbook declares.

* **No compose pack:** tag `valentus-theme` when this bundle URL (or vendored supplemental-ui) is yours.
* **facto-stack hub:** tag `facto-stack` **only**. The pack is the provider and pairs with this bundle, so the hub does *not* also carry `valentus-theme`, and not linkinator, page-edit, antora-search-chat, nav-typology, page-context, site-nav-tree, soft-nav-page-toc, or any other member. The bundle URL is a rolling `v3` asset with no pin to bump.

Hub checklist: link:https://docs.antora-supplemental.org/docs/hub-github-topics/[Hub GitHub topics^].

CLI (merge-safe — fetches existing topics first):

[source,bash]
----
REPO=owner/docs-repo   # playbook repo
TOPIC=valentus-theme
EXISTING=$(gh api "repos/$REPO/topics" -H "Accept: application/vnd.github.mercy-preview+json" --jq '.names')
# merge TOPIC into EXISTING, then:
gh api -X PUT "repos/$REPO/topics" \
  -H "Accept: application/vnd.github.mercy-preview+json" \
  --input - <<< '{"names":["valentus-theme", /* …keep prior topics… */]}'
----

Or use the registry helper once you have `antora-registry-topics.json5` / dependent lists: see the Antora Extensions Registry contributing guide (*Product dependency topics*).

== Theme repository itself

The `antora-supplemental/valentus-theme` repo carries:

* **Product identity:** `valentus-theme`
* **Gallery / capability:** `antora-theme`, `antora-light-theme`, `antora-dark-theme` (and related UI topics)

`antora-registry-topics.json5` at the repo root lists the intended set for `scripts/apply-registry-topics.mjs` in the extensions registry.

== Rediscovery

[source,bash]
----
gh search repos --topic valentus-theme
# or
gh api "search/repositories?q=topic:valentus-theme"
----

== Convention (all themes)

Any published Antora UI theme should document the same rule:

* Theme **product** topic = GitHub repository name (for example `valentus-theme`, `architexture-theme`).
* **Dependents** (playbook repos) add that product topic when they adopt the theme *without* a compose pack. Hubs on a pack that pairs with the theme (facto-stack) tag the pack instead.
* Gallery filters keep using capability topics (`antora-theme`, appearance tags) — do not replace those with the product name alone on the theme repo.

See also: link:https://github.com/antora-supplemental/antora-extensions-registry/blob/main/docs/modules/ROOT/pages/contributing.adoc[Registry contributing — GitHub Topics^].
